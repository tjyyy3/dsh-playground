# 发布与更新

每个版本使用固定的 Git tag 和 GitHub Release 安装包。正式版使用 `v0.5.0` 这样的 tag，Beta 可以使用 `v0.6.0-beta.1`。`preview`、`beta`、`rc` 都按预发布处理。

## 准备候选版本

1. 在 PR 中同步更新 `package.json`、`package-lock.json` 和 README 徽章版本。
2. 运行 `npm ci` 和 `npm test`。
3. 在干净的候选检出中运行 `npm run release:pack -- --tag v0.5.0-preview.8`。按待发布版本替换 tag。产物位于 `_scratch/release/`，包括 `.tgz` 和 `SHA256SUMS`。
4. 用这个安装包验证下方的安装清单，记录 DSH 版本、操作系统及结果。
5. 合并通过检查的 PR，在合并后的提交创建与包版本一致的 tag 并推送。

## 生成 Release 草稿

在 GitHub Actions 手动运行 **Prepare release**，填写已有 tag。工作流验证 tag 指向 main 的提交、版本一致、Windows 和 macOS 的 Node 24 与 26 测试通过、打包内容齐全，然后创建带安装包和 SHA-256 校验文件的 Release 草稿。

带预发布后缀的版本会勾选 **Pre-release**。正式版发布前确认没有勾选该项，并将其设为最新正式 Release。检查草稿的更新说明和已知限制后发布，用户才能在插件中查到。

重复运行会拒绝覆盖已存在的 Release。已有草稿可继续检查并发布，已发布版本的修复使用新版本号。

## 验证安装与切换

在独立的 DSH 配置和测试工作区执行以下操作。

- 首次安装。使用原生插件安装框安装候选包，启用后确认 Playground 可打开，运行版本和安装包相同。
- 旧版升级。先安装上一版，再按对应 DSH 的流程更新。DSH 0.2.1-rc.5 的第三方插件流程可能要求卸载后重新安装。记录需重启时的提示，重启后再次核对。
- 返回旧版。安装已验证兼容的旧包，确认测试工作区、对话与已有任务仍可读取。涉及数据格式迁移时，先备份再验证旧版读取能力。
- 失败恢复。用缺少必要元信息的测试包触发安装失败，核对磁盘版本、依赖记录和启用状态，再重新安装已知可用版本。
- 发布来源。发布后从 GitHub Release 下载包并核对 SHA-256，再测一次安装。GitHub 下载错误和 npm 依赖下载错误分别记录。

测试记录要区分 DSH Desktop 与 DSH Web。Web 的安装结果不能直接记作桌面安装已通过。

## 版本卡片的行为

卡片显示本进程加载的插件版本。打开设置只读取本地版本，用户点击 **检查更新** 才访问固定仓库的公开 Releases API。

正式版渠道只选择正式发布。Beta 渠道选择版本号最高的正式或预发布版本。选择渠道只影响此次检查目标，用户主动下载安装包后才更换版本。

尚无对应 Release、网络失败或下载包缺失会显示不同状态。切回正式版可能降低版本号，应先核对该版本的数据兼容说明。

GitHub tags 和已合并提交本身不会出现在更新列表里。只有公开发布的 Release 才进入列表。仓库暂不通过 npm 发布插件，后续可以在确认包名权限后接入 `latest` 和 `beta` 标签。
